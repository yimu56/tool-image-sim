# 机台图片模拟器（imgsim）

一个 Windows 桌面小工具，用来**模拟生产机台持续产出图片**：按设定频率，把指定尺寸、指定文件大小的随机图片写入指定目录。适用于压测图片采集、落盘、上传、质检等链路，不需要真实相机或产线设备。

GUI 基于纯 Go 的原生控件（lxn/walk），编译结果是单个 exe，不需要 .NET、Java、gcc 或任何运行库。

---

## 快速开始

1. 先双击 `build.bat` 构建（或按下方「从源码构建」命令），再双击生成的 `dist/imgsim.exe`。
2. 填好尺寸、目标大小、生成间隔、输出目录；需要无人值守时再填「运行时长」或「生成张数」作为停止条件，点「开始生成」，点「停止」结束。
3. 首次开始生成时会在 exe 同目录写出 `config.json`，下次启动自动回填上次参数。

默认输出位置是 exe 同目录下的 `output\yyyyMMdd\`；运行日志同时追加到 exe 同目录的 `logs\imgsim_yyyyMMdd.log`。

## 界面参数

| 参数 | 说明 | 取值范围 |
|---|---|---|
| 宽度 / 高度 | 图片像素尺寸 | 8 ~ 16000 px |
| 目标大小 | **文件字节数**，不是"大约" | 1 ~ 204800 KB |
| 图片格式 | JPG / PNG / BMP | 默认 JPG |
| 图片风格 | `original` 原始随机噪声 / `minecraft` 本地方块化转换 | 默认 `original` |
| JPEG 质量 | 仅 JPG 生效，直接参与编码 | 1 ~ 100，**默认 100** |
| 预计文件大小 | 按当前配置预测的**单值**文件字节数（含图像数据与填充量拆分） | 只读，参数一变即刷新 |
| 满细节自然体积 | 最高细节档位下的图像数据量，**不受目标大小钳制**，随分辨率变化 | 只读，参数一变即刷新 |
| 压不到目标时自动降质量 | 目标过小、细节降到最低仍超时，允许内部下调质量 | 默认开 |
| 严格填充到目标大小 | 用图片元数据把文件补齐到精确字节数 | 默认开 |
| 按日期建子目录 | 输出目录下再建 `yyyyMMdd` 子目录 | 默认开 |
| 生成间隔 | 两张图片之间的间隔 | 10 ~ 3600000 ms |
| 运行时长 | 到点自动停止；0 表示不限 | 0 ~ 10080 分钟（7 天） |
| 生成张数 | 到量自动停止；0 表示不限；每轮从 0 重新计数 | 0 ~ 1000000000 |
| 文件名前缀 | 会过滤 Windows 非法字符 | 如 `LINE-A` |
| 输出目录 | 可手填、「浏览...」选择、「打开」直接打开 | 任意可写目录 |

文件命名：`前缀_yyyyMMdd_HHmmss.mmm_轮数_本轮序号.jpg`，例如 `IMG_20261110_163359.176_001_000655.jpg` 表示第一轮生成的第 655 张。轮数为 3 位，每次点击「开始生成」递增；本轮序号为 6 位，每轮从 `000001` 重新计数。**轮数只在本次进程内累计，不写入 `config.json`**，重新打开软件后从 `001` 重新开始；毫秒时间戳保证跨轮文件名不会互相覆盖。

按钮：`开始生成` / `停止` / `清空日志` / `打开日志`；右侧状态栏显示已生成张数（设了上限时附带「上限 N 张」）、失败数、累计体积、单张耗时。

**运行限制**：`运行时长` 与 `生成张数` 可单独或同时设置，**满足任一条件即自动停止**，并在日志里写明原因（如「任务已停止：已达到生成张数上限（1000 张）」）。两者都为 0 时保持原来的手动停止行为。张数按「本轮已尝试生成数」计，正常情况下即本轮落盘文件数；即使持续失败也不会无限重试。**每次重新点击「开始生成」都会把张数计数清零**：第一轮生成 100 张后，把上限改成 50 再开始第二轮，仍会完整生成 50 张。开始日志会标注「第 N 轮开始生成」。

## 文件大小为什么能精确到字节

1. **档位自适应探测**：每测一个纹理档位都要全量渲染 + 编码一次，是整条链路最贵的操作。因此先测 0~110 档的中点，按实测体积决定「往下找 / 直接收工 / 往上找」，只在必要时才在对应区间二分。开启「严格填充」时，缺口小于目标 10% 就停止搜索、剩余交给填充；关闭填充时缺口小于 2.5% 才停，尽量让真实图像内容占满体积。
2. **质量二分**（可选）：若连最平滑的画面都超过目标，且勾选了「自动降质量」，JPEG 会自动下调质量再试。
3. **元数据填充**：剩余字节用合法的元数据块补齐 —— JPEG 用 `COM` 注释段（超过 65533 字节自动分段），PNG 用 `tEXt` 块，BMP 直接在像素数据后补零。解码器会忽略这些数据，**文件仍是完全合法、可正常打开的图片**。

所以 `ls` / 资源管理器里看到的大小严格等于 `目标大小 × 1024`。日志中的 `细节 x.xx` 是本次实际采用的纹理档位，`质量 xx` 是实际采用的 JPEG 质量。

> PNG/BMP 不使用质量参数。BMP 无压缩，大小由尺寸决定（宽 × 高 × 3 + 54 字节），此时目标大小仅在大于该值时有效。

### 质量与大小的取舍

- **大小优先**：保持「严格填充」+「自动降质量」开启，任何合理目标都能精确命中，代价是内部可能自动调低质量。
- **画质优先**：设定质量后取消「自动降质量」。若该质量下最小体积已超过目标，程序会输出可达到的最小文件并在日志明确提示「请调低质量、放大目标或勾选自动降质量」，**不会偷偷改掉设定的质量**。
- 目标大小低于该尺寸的编码下限时无法再压（例如 800×600 PNG 下限约 123 KB），日志会注明下限值。
- 默认质量已从 88 调为 **100**。它只影响界面与 `config.json` 的默认值；`Spec` 未显式指定质量时的内部兜底仍为 88，保证既有调用与回归基线不变。质量 100 编码体积更大，在默认 800KB 目标下会选到更平滑的细节档位（实测约 `细节 0.05`），但质量本身不会被偷偷下调。

## 预计文件大小

「图片参数」里有两行只读指标：**预计文件大小**与**满细节自然体积**，随宽度、高度、图片格式、JPEG 质量、图片风格、目标大小、两个开关实时刷新。显示的是确定值，不再是区间，例如：

```
预计文件 800 KB（图像数据 ≈ 758 KB + 填充 42 KB）
2.3 MB（满细节；图像数据已自动降档至 758 KB 以命中目标）
```

- **口径**：把当前配置等比缩小成一张小采样图（默认上限 480×360），跑**与真实生成完全相同**的 `Build` 档位探测 / 质量二分 / 编码，再把编码体积按面积比还原。因此预测的是「这套配置实际会编码出多少图像数据」，而不是理论上下限；默认配置下与真实产物的图像数据体积偏差约 1.3%（`TestEstimateDefaultConfigMatchesRealBuild` 锁住 ≤25%）。
- **单值的三部分**：`预计文件` 是最终落盘字节数；`图像数据` 是编码后未填充的体积；`填充` 是元数据补齐量。开启「严格填充」时文件字节数恒等于 `目标大小 × 1024`（除非目标低于可编码下限，此时会明确提示「目标低于可编码下限，无法精确命中」）。关闭填充则预计文件 ≈ 图像数据。
- **为什么图像数据会卡在目标附近**：档位探测会按目标大小自动选择合适的纹理细节档位。目标较小时会主动降低细节，因此不同分辨率的「图像数据」都被压到目标附近 —— 目标 2048KB 时，`1920×1080` 与 `1920×3000` 都显示约 `1.9 MB`，真实产物也确实是 `1.79~1.85 MB`（前者细节档位 0.12，后者降到 0.01）。这是自适应体积控制的结果，不是估算错误。
- **满细节自然体积**：额外用最高细节档位（`amp=1.0`）在采样图上编码一次，再按面积还原；不做任何目标钳制，只由分辨率 / 格式 / 质量 / 风格决定，因此能直观看出分辨率对图像数据量的影响。实测 `JPG / 质量 100 / 目标 2048KB`：`1280×960` ≈ 2.3 MB、`1920×1080` ≈ 3.9 MB、`1920×3000` ≈ 10.7 MB、`3840×2160` ≈ 15.5 MB。该项不参与落盘预测，`预计文件` 与 `图像数据` 仍沿用原有真实产物口径。
- **实时性**：`lxn/walk` 在 `GroupBox` 内不转发 `EN_CHANGE`，`LineEdit.OnTextChanged` 不可靠，因此由 `logPump` 每 100ms 在 UI 线程比对参数快照；变了才重算（相同快照命中缓存，几乎零开销）。单次估算约 20~65ms（含满细节编码），同步执行、不卡界面。`TestEstimateUIRealtimeRefresh` 用真实窗口绑定回归这条链路。
- **BMP**：无压缩，直接给出 `54 + ((宽×3+3)&^3) × 高`，不做渲染；此时自然体积等于文件体积。
- **风格**：选择 `minecraft` 时按转换后的画面预测，明显小于 `original`。
- **超大尺寸**：等比采样后按面积还原，填 16000×16000 也不会把内存和 CPU 打满；过大的目标会在采样侧收敛到采样图原始数据量上界，避免为填充申请大块内存。
- 估算使用独立固定种子，与产线 `frameSeed` 完全隔离，**不消耗也不改变任何真实生成的随机状态**；由 `TestEstimateDoesNotAffectBuild` 与 8 组 golden 回归共同保证。

> 实测：默认 `1280×960 / JPG / 质量 100 / 目标 800KB` 显示「预计文件 800 KB（图像数据 ≈ 758 KB + 填充 42 KB）」。把质量改 20 → 图像数据 332 KB；宽度改 640 → 168 KB；目标改 2000KB → 预计文件 2.0 MB；关掉严格填充 → 预计文件 168 KB。数字随参数即时变化。

## 图片风格

界面「图片风格」下拉框、`config.json` 的 `style` 字段、命令行 `-style` 三处等价，优先级：`-style` > `config.json` > 默认。

| 风格值 | 说明 |
|---|---|
| `original`（默认） | 原始随机噪声图。**不执行任何后处理**，随机源、种子、尺寸、频率、体积控制与 v1.1 完全一致 |
| `minecraft` | 在上述原始图生成之后做一次本地转换：8×8 方块化 → 块平均色/亮度 → 程序化近似色板（水/沙/草/石/雪/泥土等，按亮度分 6 档 × 3 色相族）→ 5 级明暗与上下沿阴影 |

要点：

- **不是重新生成一张图**：`minecraft` 的每一次探测都先调用原来的 `renderRGBA`（同一个种子、同一个细节档位），再对这张图做转换，因此原始随机性和低频明暗斑块结构被保留下来；块内纹理用块坐标 + 原图统计值的确定性哈希，不引入新的随机源。
- **纯本地、纯标准库**：没有在线 AI API、没有网络请求、没有新增依赖、没有 CGO；色板是代码里定义的近似色，未使用 Minecraft 官方纹理素材。
- **尺寸严格等于设定值**，生成间隔、文件名、种子语义不变，输出仍是合法的 JPG/PNG/BMP。
- 枚举实现为可扩展注册表（`style.go` 的 `styles` + `styleTransforms`）：新增风格只需加常量、注册一个 `func(*image.RGBA) *image.RGBA`、追加到列表，界面下拉框自动带上新项。
- **非法值**（如 `style: "pixel"`）一律回退 `original`，并写一条 `[style] 未知图片风格 ... 已回退到默认风格` 日志（GUI 运行日志 / `-once` 终端）。
- **默认 `original` 下有哪些「看起来不一样」**：`config.json` 多了一个 `style` 字段、`_说明` 文案增加了风格说明；GUI 多了「图片风格」下拉框；`-once` 输出末尾多了 `style=original`。**这些都是配置/界面/日志层面，图片字节、尺寸、生成频率与体积控制完全没有变** —— `original_golden_test.go` 用改造前 8 组固定参数（含默认 1280×960/800KB）的产物 SHA-256 做逐字节回归。
- 每帧种子本来就是 `纳秒时间戳 XOR 递增序号`，**改造前后每一张图都不同**。要对比改造前后请用同一种子固定参数（如上面的 golden 回归），不要拿两次独立运行的两张图直接比。

### 风格对文件大小的影响（重要）

方块化 + 有限调色板会让图像**明显更容易压缩**，同尺寸下编码体积通常远小于 `original`。处理策略：

1. 体积档位探测、JPEG 质量二分、自动降质量全部在**转换后的画面**上执行，也就是搜索的是「转换后要占多少字节」，不会拿原始图的体积去猜。
2. 若编码结果小于目标，沿用原有合法的元数据块（JPEG `COM` / PNG `tEXt` / BMP 尾部补零）补齐到精确字节数，**文件仍是完全合法的图片，尺寸不变**；补齐字节数写进该张图片的日志备注（`风格 minecraft：... 已用原有元数据填充补齐 N 字节到目标（尺寸不变）`）。
3. 未勾选「严格填充」时不会悄悄补齐，备注明确写「比目标小 N 字节，未做填充」。
4. 目标低于该尺寸编码下限时，仍按原有逻辑输出最小文件并在备注里说明下限；BMP 无压缩，大小依旧由尺寸锁定。
5. 启动时会额外记录一条风格说明日志；非原始风格的每张图片日志追加 ` 风格 minecraft` 标记，`original` 的日志文本保持原样。

> 也就是说：`target_kb` 依旧是「文件字节数」而不是「图像信息量」。压力测试语义没有被静默改变，只是图像数据占的比例变小、元数据占的比例变大，这一点在日志和备注里都是可见的。

## 日志

- **每张图片一行**，不丢行、不跳号。v1.0 曾为保护界面做过「前 20 条 + 每 20 条一条」的节流，看到 `[10]` 直接跳到 `[30]` 就是这个原因；v1.1 已彻底移除。
- 每行包含：序号、文件名、实际大小、耗时、细节档位、JPEG 质量、**内容指纹 `#xxxxxxxx`**、填充状态。指纹是整份文件 SHA-256 的前 4 字节，用来直观确认每帧画面确实不同。
- 为了在高频生成时也不卡界面：一次日志写入分流到**文件队列**与**界面队列**两个独立队列。文件队列由后台 goroutine 每 100 ms 批量落盘，磁盘 IO 不占用 UI 线程；界面队列由 UI 线程一次性取空、合并成一次 `TextEdit` 写入，即使界面曾因繁忙积压多个批次，恢复后也只重绘一次。日志、预计大小、状态栏三类界面更新收敛到同一次 `Synchronize`，不再各自争抢 UI 消息队列。日志最多保留最近 500 行，超过后重建并保留最近 **120 行**，重建期间关闭 RichEdit 重绘。
- **同时写入日志文件**：`<exe 同目录>/logs/imgsim_yyyyMMdd.log`，按天追加、启动时在界面日志里显示完整路径，「打开日志」按钮直接打开该目录。文件日志与界面同源分流（每 100 ms 一次批量 `Flush`），高频生成时不会逐行刷盘；它**不受界面 500 行截断与「清空日志」影响**，可完整追溯整轮压测。退出前会等待后台刷盘泵结束再关闭文件句柄，避免收尾日志丢失。
- 「清空日志」先落盘再清空，只清界面显示，文件日志继续保留；不影响正在运行的任务和统计计数。
- 单张耗时超过生成间隔时，日志会额外告警「实际频率会低于设定值」。
- 日志文件不自动轮转：按天分文件，单文件大小随运行时长增长（10ms 间隔约 20KB/s），长期无人值守请自行清理旧文件。

## 会不会生成一模一样的图片？

**不会。** 每帧随机种子由 `纳秒时间戳 XOR (本轮序号 × 黄金比例常数) XOR (轮数 × 常数)` 生成，同时驱动两层随机斑块网格和逐像素噪声。即使细节档位、质量、目标大小完全相同，每一帧的画面内容也不同；填充用的元数据虽然固定，但前面的图像数据不同，整份文件的哈希依旧不同。

`features_test.go` 中的 `TestFramesAreNeverIdentical` 连续模拟 12 帧（细节档位打满、带精确填充），同时比对**原始像素 SHA-256** 与**最终文件 SHA-256**，要求两两唯一；`TestSeedDeterminism` 另外验证「相同种子可复现」，便于问题定位。`rounds_test.go` 中的 `TestFrameSeedDistinctAcrossRounds` 额外覆盖跨轮同序号的种子唯一性。

文件名带毫秒时间戳 + 轮数 + 本轮序号。本轮序号每轮从 `000001` 重新计数，由轮数段区分不同轮次；轮数只存在于本次进程，重新打开软件后归零，毫秒时间戳保证跨轮、跨进程都不会互相覆盖。

## 命令行参数

| 参数 | 说明 |
|---|---|
| `-config <路径>` | 指定配置文件，默认 exe 同目录 `config.json` |
| `-autostart` | 启动后立即开始生成（无人值守场景） |
| `-once` | 只生成一张图片后退出，向终端打印实际大小（自检用，需从命令行运行）；按第 1 轮 / 序号 `000001` 命名 |
| `-style <风格>` | `original` \| `minecraft`；覆盖 `config.json` 的 `style`，**仅本次运行生效、不写回配置文件**，默认 `original` |
| `-minutes <分钟>` | 本次运行时长上限，到点自动停止；`0` 表示不限，省略则用 `config.json` |
| `-count <张数>` | 本次生成张数上限，到量自动停止；`0` 表示不限，省略则用 `config.json` |

`config.json` 字段：`width`、`height`、`target_kb`、`format`、`pad_to_target`、`quality`（默认 100）、`auto_quality`、`interval_ms`、`prefix`、`out_dir`、`date_subdir`、`style`、`limit_minutes`、`limit_count`。**轮数不是配置项**，不在此列表中，也不写入文件。

例如无人值守跑 1 小时或 1000 张（先到者停）：

```bat
imgsim.exe -autostart -minutes 60 -count 1000 -config D:\imgsim\config.json
```

> `-once` 自检模式只向终端打印结果，不初始化日志文件；日志文件只在实际 GUI 运行中创建。

例如只生成一张 Minecraft 风格图做自检：

```bat
imgsim.exe -once -style minecraft -config D:\imgsim\config.json
```

GUI 里选择风格后点「开始生成」即按原有机制写入 `config.json`，下次启动自动回填；`-autostart` 无人值守时会按 `config.json`（或被 `-style` 覆盖）的风格运行。

> **默认风格不会被临时试跑改掉**：`-style` 只影响本次运行，即使配合 `-autostart`，写回 `config.json` 时也会还原磁盘上原有的 `style`。只有「在 GUI 里主动改下拉框并点开始」才会持久化。若之前已把默认写成 `minecraft`，把下拉框改回 `original` 再点一次开始，或直接把 `config.json` 的 `style` 改成 `"original"` / 删除该字段即可恢复。

## 从源码构建

环境：Windows + Go 1.21 或更高版本，**不需要 gcc / CGO**。

双击 `build.bat`，或手动执行：

```bat
go mod tidy
go build -trimpath -ldflags="-H windowsgui -s -w" -o dist\imgsim.exe .
```

`app.manifest` 与 `rsrc.syso` 提供现代控件外观和 DPI 感知，已随源码提供。若要重新生成 `rsrc.syso`：

```bat
go install github.com/akavel/rsrc@latest
rsrc -manifest app.manifest -arch amd64 -o rsrc.syso
```

国内网络建议设置 `GOPROXY=https://goproxy.cn,direct`。

## 性能

探测次数优化后（Intel Core Ultra 5 125H / Go 1.26.5，同进程对比取 4 轮最小值）：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 默认 1280×960 / 800KB JPG | 185 ms | **55 ms** |
| 320×240 / 512KB JPG（主要靠填充） | 28 ms | **8 ms** |
| 单张分配内存（默认场景） | 18.8 MB | 6.9 MB |

主要措施：中点档位一次探测即可收工、精确填充时 10% 容差提前结束、最平滑画面在质量二分里只渲染一次、噪声插值权重预计算成表、编码缓冲一次开够。大小核调度与温度会让绝对值有波动，对比请以同机同轮基准为准。

## 已知限制

1. 单张耗时随尺寸增长（1280×960 JPG 约 55~80 ms，视 CPU 而定）；间隔设得比耗时更短时实际频率会低于设定值，日志会告警。
2. 目标大小低于编码下限时无法精确命中，日志会说明下限值。
3. BMP 无压缩，大小由尺寸锁定。
4. 生成的是合成纹理（随机斑块 + 传感器噪声），用于链路压测，不是真实工件照片。
5. `minecraft` 是程序化近似风格，不含任何官方纹理；方块化后图像数据占比下降，精确体积主要靠元数据填充（见「风格对文件大小的影响」）。
6. 「预计文件大小」是固定种子下的采样预测，不是承诺：实际编码体积随每帧随机内容小幅波动；默认配置下与真实产物偏差约 1~2%。
7. 时长上限在「每张开始前」检查，最后一张可能略微超出设定时长（最多一张的生成耗时）；张数上限精确不超。
8. 「满细节自然体积」同样是按采样图面积还原的估算值，用于对比分辨率影响，不代表实际落盘的图像数据字节数；实际图像数据会被目标大小钳制。
9. 日志文件按天分文件、不自动清理，长期运行请定期归档 `logs\` 目录。
